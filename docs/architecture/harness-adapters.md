# Harness Adapter Contract

> SSOT for how this template adapts to AI coding harnesses.
> Routing and constraints still live in `AGENT.md`; this file explains tool-specific entry points and capability differences.

---

## Adapter principle

Every supported harness should reach the same canonical router:

```text
harness entry point -> AGENT.md -> task routing -> docs/rules/context/skills
```

The adapter entry point must stay thin. It may point to `AGENT.md`, but it must not duplicate routing logic, hard stops, facts, rules, or skills.
This template commits the generated one-line entry points so every supported harness has an immediate path to the same router.

Portable AI assets live in `plugins/`:

```text
plugins/ -> tools/adapters/ -> harness-native rules/context/skills
```

Use harness-native generated artifacts when available. Explicitly reading `.cursor/context/` or `.cursor/skills/` outside Cursor is only the fallback when a harness lacks native discovery for the needed asset.
Non-Cursor generated skill directories include README indexes that explain the generated skills and point back to `AGENT.md`, `docs/SSOT-map.md`, and plugin sources for context.

---

## Adapter manifest

The machine-readable adapter registry lives in:

```text
tools/harness_adapters.json
```

This manifest is the implementation source for:

- `tools/setup_harness.py` — generates harness entry points
- `tools/validate_harness.py` — validates generated entry points
- `tools/validate_template.py` — checks adapter metadata and docs wiring

When adding or changing a harness, update the manifest first, then update this document if the capability matrix or workflow changes.

## Generated entry-point contract

Committed harness entry points must contain exactly:

```text
AGENT.md
```

This keeps `AGENT.md` as the single router. If a harness needs extra setup, document that setup here or in `SETUP.md`; do not put extra instructions into the generated entry file.

Generated harness-native assets are different from entry points. They are produced from `plugins/` by `tools/generate_adapters.py` and may contain skills, generated README indexes, Cursor MDC rules, or Cursor context providers.

## Validation

Use these checks after changing adapter files:

```bash
python tools/validate_harness.py --strict
python tools/validate_template.py
```

Use strict harness validation for this template because the entry points are committed:

```bash
python tools/validate_harness.py --strict
```

Run the full validation suite with the cross-platform Python entry point:

```bash
python tools/check_template.py
```

If `make` is available, `make check` runs the same Python entry point.

## Setup commands

Inspect supported generated harnesses:

```bash
python tools/setup_harness.py --list
```

Inspect adapter loading behavior for all tools:

```bash
python tools/setup_harness.py --describe
```

Preview generated entry points without changing files:

```bash
python tools/setup_harness.py --all --dry-run
```

Generate selected entry points:

```bash
python tools/setup_harness.py --harness codex claude_code --commit
```

Generate every generated adapter:

```bash
python tools/setup_harness.py --all --commit
```

Generate Cursor rules/context/skills from `plugins/`:

```bash
python tools/generate_adapters.py --harness cursor
```

Preview all harness-native assets:

```bash
python tools/generate_adapters.py --all --dry-run
```

Generate all harness-native assets:

```bash
python tools/generate_adapters.py --all
```

## When adding a new harness

1. Add or update the adapter row in `tools/harness_adapters.json`.
2. Add a template under `tools/harness_templates/` if the adapter has a generated entry point.
3. Add a generator under `tools/adapters/` if the harness has native rules/context/skills output.
4. Add the adapter to `tools/generate_adapters.py`.
5. Add a row to the capability matrix above.
6. Add or update checks in `tools/validate_template.py` if the contract changes.
7. Run `python tools/validate_template.py` and `python tools/validate_harness.py --strict`.
